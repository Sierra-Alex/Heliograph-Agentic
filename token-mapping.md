# Token Mapping — Figma to Code

This doc explains how a token defined in Figma (via Token Studio) becomes a
real value in code, so anyone — human or Claude Code — can predict one from
the other without cross-checking both sides every time.

It documents **rules and exceptions**, not a token-by-token list. The full,
always-current list of real tokens lives in the build output (see below) —
this doc would go stale immediately if it tried to duplicate that list by hand.

## Where tokens actually live

| File | What it is |
|---|---|
| `tokens.json` | Source of truth. Written by Token Studio. One JSON object per token set (`primitive`, `semantic`). |
| `build/css/variables.css` | Auto-generated by Style Dictionary. CSS custom properties, e.g. `--color-background-brand`. **Do not hand-edit.** |
| `build/ts/tokens.ts` | Auto-generated by Style Dictionary. Typed TS constants, e.g. `colorBackgroundBrand`. **Do not hand-edit.** |

If you need to know "does this token exist, and what's it called in code?" —
check the build files. They're regenerated by `npm run build:tokens` and are
never out of date with `tokens.json`.

## Naming transform rules

1. **Token set name is dropped.** `primitive` / `semantic` exist to organize tokens
   inside Token Studio — they aren't part of the token's identity in code.
2. **Nested groups become dash-separated, lowercase.** e.g. a token at
   `color.background.brand` becomes `color-background-brand`.
3. **CSS output:** `--` prefix + kebab-case → `--color-background-brand`
4. **TS output:** camelCase, no prefix → `colorBackgroundBrand`
5. **Symbols get stripped, including minus signs.** `%`, `+`, and `-` aren't
   valid in a CSS variable name, so they're removed entirely when generating
   the output name. This is the root cause of the exception below.

## Known exception: signed values

Because the minus sign gets stripped, a token named `2%` and a token named
`-2%` collide into the identical output name (`2`) — one silently overwrites
the other. We hit this for real with letter-spacing.

**Rule going forward: positive and zero values stay unprefixed. Negative
values get a `negative-` prefix.**

| Figma name | Status |
|---|---|
| `2%` | unprefixed (positive) |
| `0%` | unprefixed (zero) |
| `-1%` | renamed to `negative-1%` |
| `-2%` | renamed to `negative-2%` |

Apply this same rule to any *future* token where a positive and negative
version of the same magnitude could both exist — spacing, opacity nudges,
etc. Check before naming a new token, not after the build warns you.

## Primitive vs. semantic — which one do I use?

- **Primitives** (raw values, e.g. a specific blue, a specific gray scale
  step) describe *what a value is*. Never reference a primitive directly
  inside a component.
- **Semantics** (e.g. `color-background-brand`, `color-text-primary`)
  describe *what a value is for*. Components should only ever reference
  semantic tokens.
- If a component needs a value that has no semantic token yet, that's a
  signal to create one — not a reason to reach for the primitive directly.
  This is what keeps a rebrand or theme change a one-place edit instead of
  a find-and-replace across every component.

## Known open gaps

- **20 typography tokens** are missing `letterSpacing` / `paragraphSpacing` /
  `textCase` sub-values (surfaced as non-blocking build warnings). Not yet
  triaged — revisit before assuming typography tokens are fully specified.

## Keeping this doc current

This file should rarely need edits, because it documents rules, not tokens.
Update it only when:
- A new category of naming collision is discovered — add it under
  "Known exception."
- The primitive/semantic usage policy changes.
- The actual transform rules change (i.e., `style-dictionary.config.mjs`
  changes in a way that affects output naming).
